# Stored facts carry their links; targets are never inferred from shape

## Status

Accepted

## Context

Applying a principal override (ADR 0011) means deciding, for each stored fact, which override target it belongs to: an exact representation, a provider-asset row, or none. The first implementation tried to work this out at read time from the rows themselves: which transfers share a transaction, how many legs have equal amounts, which sibling has an exact observation, what a metadata blob says. Every review round found another case where such a guess attached a decision to the wrong movement, suppressed a leg that had no link to the reconciliation it was blamed on, or crossed two same-currency fees. The pattern, not the cases, was the defect: the writer knew the answer when it created the row and threw it away.

Max recorded the rule on #149 (issuecomment-5526204642):

> Stored facts are never matched to override targets by shape. Transaction, direction, amount, address, coordinate counts, sibling rows, and multiplicity may not be used to discover a fact's target. A fact either carries the target recorded by the writer, or it is replayed to regenerate that link, or the adapter returns a typed blocker.

## Decision

The code that creates a fact records every link a later reader needs. Readers look links up; they never reconstruct them.

- Provider transfers, canonical transfers, and transaction legs carry a first-class link to the source representation use they came from, or to the provider-asset row, as the producer knew it. A canonical transfer's target reaches its leg only through the leg's explicit source-transfer link.
- A transaction leg records an explicit **origin kind**: `provider_transfer` with the exact provider-transfer ID, `canonical_transfer` with the exact source-transfer ID, or `none`. A null is never read as a meaning.
- Custody movements reach their targets through their existing origin and reconciliation links. No target columns are duplicated onto them.
- Producer contracts carry what the producer knows, as tagged values. A candidate whose economic asset is not yet decided is a tagged candidate, not a draft with a placeholder ID. A value must mean what its type says: a provider-row UUID is never put in an economic asset field, a required new column never gets a default that records a false fact, and a required fact is never staged as nullable.
- A fact that should have a link but has none produces a typed blocker. It is never silently dropped and never matched to a sibling. Grouping may enforce that one transaction is withheld as a whole; it may not discover identity.
- Historical rows get their links back by replaying the source through the normal writer. Never by SQL backfill, tuple inference, or matching stored rows. When a new required recorded-fact column cannot be filled truthfully for existing rows, the table is cleared and regenerated by replay — the clearing happens in a one-off script outside the migration, which stays schema-only (amended 2026-09-05: in-migration clearing exception revoked; see AGENTS.md, Database, and the correction comment on #149).

## Considered options

- Read-time matching with more special cases was rejected. Each case was a new way to be wrong, and none could be proven complete.
- SQL backfill of links from existing columns was rejected. It is matching by shape done once, and it writes the guesses into the fact tables.
- Nullable staging columns filled later were rejected. They ship the ambiguous null the rule forbids and need a second migration.

## Consequences

- A fix that starts adding matching, grouping, or counting over stored rows is a signal that a recorded fact is missing. Stop, name the missing fact, and record it at the writer.
- Producer contract changes fan out into test fixtures that build rows directly. Those fixture edits are mechanical alignment and are reviewed as a category, separate from the production change.
- Replay is the repair path for stored facts. Deleting derived rows and replaying them is normal pre-launch procedure, not an incident.
- The same rule applies beyond overrides: any later reader that needs to know where a row came from should find that answer stored on the row.
